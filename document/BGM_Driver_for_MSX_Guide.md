# 第1章 BGM Driver の概要

## 1.1 BGM Driver とは

BGM Driver（リポジトリ名 bgm_driver）は、MSX 用のゲームプログラムに組み込んで使うことを想定した、PSG 専用の BGM・効果音演奏ドライバである。作者が 2009 年頃に MSX 用ゲーム制作の資料をまとめていた際に、ゲーム用の BGM ドライバとしてゼロから作成したもので、2020 年 7 月に MIT ライセンスで公開された。

対象とする音源は、MSX の標準 PSG（AY-3-8910 および互換チップ）だけである。PSG の 3 チャンネルを BGM の 3 パートに割り当て、そのうち第 3 チャンネルを効果音と共用する、ゲーム用途に割り切った構成になっている。PSG のハードウェアエンベロープは使わず、音量の時間変化はすべてソフトウェアで生成する。その代わりに、音色ごとにビブラート波形と ADSR 型エンベロープを持つ、PSG としては手の込んだ音作りができる。

ドライバ本体は Z80 アセンブリ言語（ZMA 記法）で書かれた 2 つのソースファイルだけであり、自分のプログラムに include して使う。曲データは、専用の MML コンパイラ mc.exe で MML テキストから生成するのが標準の方法である。効果音データにコンパイラはなく、定数を並べたバイト列として手作業で作成する。

本書は、このドライバについて次の 3 点を、ソースコードに基づいて解説する資料である。

1. **コードの原理解説**（第 3 章）： 割り込み駆動の仕組み、データのデコード、エンベロープやビブラートの処理、BGM と効果音の共存の仕組み。
2. **曲データの作り方**（第 4 章・第 5 章）： MML の文法と mc.exe の使い方、生成される曲データのバイナリ形式。
3. **効果音データの作り方**（第 6 章）： 効果音データの形式、コマンドの意味、優先度の規則、BGM と競合したときの挙動。

API の呼び出し仕様そのものは、リポジトリに付属する『bgm_driver API Reference Manual』（document/bgm_driver_api_reference.pdf）が公式のリファレンスである。本書でも組み込みに必要な API は第 2 章で一通り説明するが、レジスタの破壊条件などの細部は API リファレンスと併せて参照してほしい。なお本書の記述は、すべてリポジトリのソースコード（bgmdriver.asm、mc.c など）を根拠としており、既存資料の記述と実装が食い違う箇所では実装に合わせて記述し、その旨を付録 B にまとめた。

## 1.2 特徴と制限

ソースコードから読み取れる本ドライバの特徴と制限を整理する。

| 項目 | 内容 |
|---|---|
| 対応音源 | PSG（AY-3-8910 互換）のみ。I/O ポート A0h（アドレスラッチ）／A1h（データライト）へ直接出力する |
| BGM チャンネル | 3 チャンネル（PSG のトーン 3 系統に 1 対 1 で対応） |
| 効果音 | 1 系統のみ。第 3 チャンネルを BGM と共用する（和音の効果音は不可） |
| 音色 | 曲データ内に複数定義可能。32 ステップのビブラート波形＋AR／DR／SL／SR／RR＋ビブラート遅延＋ノイズ周波数＋ドラム用基準周波数、の 41 バイト構成 |
| ドラム音 | 5 種類まで。音色を割り当ててトーン／ノイズで打楽器を模す |
| エンベロープ | ソフトウェア処理（PSG のハードウェアエンベロープは使用しない） |
| ループ | チャンネルごとに 1 か所のループ開始位置（MML の $）を指定可能 |
| フェードアウト | マスター音量を一定間隔で下げていく方式。効果音の音量には影響しない |
| 割り込み | 1/60 秒周期の呼び出しを利用者側で用意する（H.TIMI フックが標準）。ドライバ自体はフックを持たない |
| 配置 | コードとワークエリアは RAM 上に置く。割り込みから参照するため、ページ 0（0000h〜3FFFh）への配置は不可（第 2 章） |

制限として意識しておくべき点は次のとおりである。

- **テンポはデータに残らない**。MML のテンポは mc.exe がコンパイル時に各音符の待ち時間へ換算してしまう。演奏中にテンポを変える仕組みはない。
- **ノイズは PSG 全体で 1 系統**しかない。複数チャンネルがノイズを使う場合、ノイズ周期は共有され、最後に有効化したチャンネルの値が優先される（3.8 節）。
- **効果音の再生中、第 3 チャンネルの BGM は無音になる**。シーケンス自体は進み続けるため、効果音が終わると途中から聞こえるようになる（3.9 節）。

## 1.4 本書の表記

- 16 進数は、本文では末尾に h を付けた表記（例： A000h、FD9Fh）を用いる。ソースコードの引用中では、元のソースの表記（0xA000 など）をそのまま残す。
- チャンネルの呼び方は、ドライバ内部の数え方に合わせて **ch0、ch1、ch2** とする。PSG のチャンネル A／B／C、API リファレンスの ch.1〜ch.3 と同じものを指す。効果音が使うのは ch2（PSG チャンネル C）である。
- 「フレーム」は 1/60 秒の割り込み 1 回分を指す。ドライバの時間処理はすべてこの単位で数える。
- 音の周期値（PSG のトーンピリオド）は、値が小さいほど高い音になる。周波数との関係は 3.4 節で述べる。

# 第2章 組み込みと API

## 2.1 組み込みの全体像

bgm_driver を使うために必要な作業は、次の 3 つである。

1. 自分のプログラムの任意の場所に `include "bgmdriver.asm"` と書き、ドライバ本体を取り込む（bgmdriver.asm の先頭で bgmdriver_d.asm が include される）。
2. 1/60 秒周期の割り込み（H.TIMI フック）から `bgmdriver_interrupt_handler` を呼ぶ仕掛けを用意する。
3. 曲データと効果音データを用意し、API を呼んで演奏する。

ドライバは単体では何もしないライブラリであり、割り込みの登録すら自前では行わない。これは、MSX の 1/60 秒割り込みがゲーム本体の処理など多くの用途と共用されるもので、ドライバが占有すべきではないという設計判断による（API リファレンス 2.1 節）。割り込みの登録と復元は、利用するプログラムの責任で行う。

配置上の注意が 2 つある。

- **ドライバは RAM 上に置くこと**。ワークエリアを含むため当然でもあるが、割り込みハンドラへ飛ぶためのフック書き換え先（後述のバックアップ領域）も RAM でなければならない。
- **ページ 0（0000h〜3FFFh）への配置は避けること**。この領域はスロット切り替えが頻繁に行われるため、割り込み発生時にドライバが見えなくなる恐れがある。z88dk 版サンプルの readme では「4000h 以上のアドレスを指定する必要がある」と明記されている。曲データ・効果音データの置き場所についても同じ注意が要る（割り込み処理中にドライバが参照するため）。

## 2.2 H.TIMI フックの登録

標準的な方法は、BIOS の H.TIMI フック（FD9Fh、5 バイト）を書き換えて、自作の割り込みハンドラへジャンプさせることである。sample/ の sample.asm にある interrupt_initializer が、そのオーソドックスな実装例になっている。要点は次のとおりである。

1. DI して割り込みを禁止する（書き換え途中で割り込みが入ると暴走する）。
2. H.TIMI の元の 5 バイトを、自コード内の退避領域（h_timi_next、初期値は ret が 5 個）へ LDIR でコピーする。
3. H.TIMI の先頭に JP 命令（C3h＋ハンドラのアドレス）を書き込む。
4. EI して割り込みを許可する。

割り込みハンドラ側は、A レジスタを push／pop で保存したうえで `bgmdriver_interrupt_handler` を call し、その後、退避した元のフック内容へそのまま流れる（フォールスルーする）構成である。

```
h_timi_interrupt_handler::
		push		af
		call		bgmdriver_interrupt_handler
		pop			af
h_timi_next::
		ret
		ret
		ret
		ret
		ret					; ここが元の H.TIMI の 5 バイトで上書きされる
```

A レジスタの保存が必要なのは、H.TIMI が「A レジスタに VDP ステータスレジスタ #0 の値が入った状態」で呼ばれる約束だからである（読み出すことで割り込み要因が解除されるレジスタなので、元の値を期待する他のフック利用者のために壊してはならない）。それ以外のレジスタは BIOS 側の呼び出し元が保存しているため、ハンドラ側で保存する必要はない。逆に `bgmdriver_interrupt_handler` 自体は全レジスタを破壊するので、自分の 1/60 秒処理を同じハンドラに書く場合は、その前後で必要なレジスタを自分で退避すること。

自分のゲームの 1/60 秒処理がある場合は、`call bgmdriver_interrupt_handler` の前か後に挿入する。プログラム終了時には、退避しておいた 5 バイトを H.TIMI へ書き戻してフックを復元する（z88dk 版の bgmdrv_term() がこれに当たる）。復元前に演奏を止めるには bgmdriver_stop を呼び、鳴りっぱなしの音を止めるには bgmdriver_mute_psg（2.3 節）を使う。

なお、割り込み周期は正確には 1/59.94 秒（NTSC の垂直同期）である。周期を短くして呼べば早送り、長くすればスロー再生になることが API リファレンスに明記されているが、BGM と効果音の両方が影響を受ける。

## 2.3 API 一覧

ドライバが公開する API は 8 つである。各 API の引数・戻り値・破壊レジスタはソースコードのヘッダコメントに基づく。詳細な呼び出し例は API リファレンス第 3 章を参照のこと。

| API | 機能 | 入力 | 備考 |
|---|---|---|---|
| bgmdriver_initialize | 演奏用ワークエリア（INFO×3）の初期化 | なし | 通常は呼び出し不要（ワークエリアは初期状態で初期化済み）。フック復元で強制停止した後の再開時などに使う |
| bgmdriver_play | BGM の演奏開始 | HL = 曲データの先頭アドレス | 演奏中なら現在の曲を止めてから開始する。フェードアウト状態も解除される |
| bgmdriver_stop | BGM の演奏停止 | なし | 停止中に呼んでも問題ない |
| bgmdriver_check_playing | 演奏中かどうかの確認 | なし | Z フラグ： 1 = 停止中、0 = 演奏中（3 チャンネルすべてが停止しているかで判定） |
| bgmdriver_fadeout | フェードアウト開始 | A = 速度（1〜255） | 音量が 1 段階下がる間隔をフレーム数で指定。大きいほど遅い。0 は指定禁止。無音まで下がると演奏も停止する |
| bgmdriver_mute_psg | PSG レジスタを無音に初期化 | なし | ドライバの内部変数は変更しない。フックを復元して止めた際の「鳴りっぱなし」対策用で、通常は使わない |
| bgmdriver_play_sound_effect | 効果音の再生開始 | HL = 効果音データの先頭アドレス | 優先度判定で再生されない場合がある（第 6 章） |
| bgmdriver_interrupt_handler | 演奏処理の本体 | なし | 1/60 秒周期で呼ぶ。全レジスタを破壊する |

呼び出しの基本形は次のとおりである（API リファレンスの例より）。

```
		ld		hl, TITLE_BGM		; 曲データの先頭アドレス
		call	bgmdriver_play		; 演奏開始

		ld		a, 10				; フェードアウト速度
		call	bgmdriver_fadeout	; フェードアウト開始
wait_bgm_end:
		call	bgmdriver_check_playing	; 演奏停止チェック
		jr		nz, wait_bgm_end	; 演奏中であればループ
```

bgmdriver_play に渡すのは必ず曲データの先頭アドレスであること。途中のアドレスや曲データでないアドレスを指定した場合の動作は保証されない（暴走する）と API リファレンスに明記されている。

## 2.4 初期化の手順まとめ

プログラム側の初期化は、実質的には次の順序になる。

1. （必要なら）bgmdriver_mute_psg で PSG を無音に初期化する。REG#7 には 0BFh（全チャンネルのトーン／ノイズを無効化し、ポート B を出力に設定）が書かれ、他のレジスタは 0 になる。
2. H.TIMI フックを登録し、1/60 秒ごとに bgmdriver_interrupt_handler が呼ばれる状態にする。
3. あとは任意のタイミングで bgmdriver_play／bgmdriver_play_sound_effect を呼ぶ。

bgmdriver_initialize は「演奏用ワークエリアの初期化」であり、PSG の初期化やフック登録は含まない点に注意すること。名前から受ける印象と役割が少しずれている。

# 第3章 動作原理

本章では、bgmdriver.asm の実装に基づいてドライバの動作原理を解説する。

## 3.1 割り込みハンドラの全体像

ドライバの心臓部は `bgmdriver_interrupt_handler` で、1/60 秒に 1 回呼ばれることを前提に、次の 4 段階をこの順序で実行する。

1. **各チャンネルの演奏処理**（bgmdriver_play_ch を ch0、ch1、ch2 の順に呼ぶ）： 曲データをデコードして「実効周波数」と「実効音量」を計算する。PSG へはまだ何も書かない。
2. **効果音の処理**（bgmdriver_sound_effect）： 効果音データのコマンドを解釈し、効果音用の周波数・音量・ノイズ周波数を更新する。
3. **フェードアウト処理**（bgmdriver_fadeout_proc）： マスター音量を段階的に下げる。
4. **ミキサー**（bgmdriver_mixer）： 1〜3 の結果を PSG のレジスタへ書き出す。PSG レジスタへの書き込みはこのルーチンに集約されている。

「演奏状態の計算」と「PSG への出力」を分離しているのが本ドライバの構造上の要点である。各チャンネルの処理は自分の担当する状態変数（INFO 構造体）を更新するだけで、チャンネル間の競合（ノイズ周期の共有や、効果音による ch2 の乗っ取り）はミキサーが最後に調停する。

## 3.2 演奏タスク情報（INFO 構造体）

各チャンネルの演奏状態は、19 バイトの構造体 INFO に保持される。3 チャンネル分で 57 バイトがワークエリアに並ぶ（play_info_ch0／ch1／ch2）。

| オフセット | 名前 | 内容 |
|---:|---|---|
| 0〜1 | INFO_PLAY_ADR | 曲データの読み取り位置。0 ならそのチャンネルは停止中 |
| 2〜3 | INFO_WAIT_COUNT | 次のイベントまでの残りフレーム数 |
| 4〜5 | INFO_EFF_FREQ | 実効周波数（ビブラート加算後の周期値。ミキサーが PSG へ書く値） |
| 6〜7 | INFO_TONE_FREQ | 設定周波数（音符から決まった周期値そのもの） |
| 8 | INFO_EFF_VOL | 実効音量（エンベロープと設定音量から計算した 0〜15） |
| 9 | INFO_TONE_VOL | 設定音量（VOL イベントで指定された 0〜15） |
| 10 | INFO_VIB_WAIT | ビブラート開始までの残りフレーム数 |
| 11 | INFO_ENV_STATE | エンベロープの状態（0=AR、1=DR、2=SR、3=RR、4=停止） |
| 12 | INFO_ENV_VOL | エンベロープ音量（0〜255 の内部値） |
| 13 | INFO_VIB_INDEX | ビブラート波形の読み取り位置（0〜31） |
| 14〜15 | INFO_SOUND_FONT | 発音中の音色データのアドレス |
| 16 | INFO_NOISE_FREQ | ノイズ周波数（bit7 がノイズ有効フラグ、下位 5 ビットが周期） |
| 17〜18 | INFO_SEL_SFONT | 選択中の音色データのアドレス（次の KeyOn から使われる） |

チャンネルの演奏処理（bgmdriver_play_ch）は、まず INFO_PLAY_ADR が 0 でないか（演奏中か）を見て、次に INFO_WAIT_COUNT が残っていればそれを 1 減らしてビブラートとエンベロープの更新だけを行い、0 であれば曲データの次のイベントをデコードする、という単純なステートマシンである。

## 3.3 データのデコード

曲データは「イベントコード＋付随データ」の列であり、デコードは先頭の 1 バイトの値で分岐する（詳細な形式は第 5 章）。

| コード | 意味 | 付随データ |
|---:|---|---|
| 0〜95 | 音符の KeyOn | 待ち時間 |
| 96〜100 | ドラム音の KeyOn | 待ち時間 |
| 101 | KeyOff | 待ち時間 |
| 102 | 休符 | 待ち時間 |
| 103 | 音量設定（VOL） | 音量 1 バイト |
| 104 | 音色設定（SOUND_FONT） | 音色データへのオフセット 2 バイト |
| 105 | ジャンプ（JUMP） | ジャンプ先オフセット 2 バイト |
| 106 | 演奏終了（PLAY_END） | なし |
| 107〜111 | ドラム 1〜5 の音色設定 | 音色データへのオフセット 2 バイト |

処理のしかたはイベントの種類で 2 つに分かれる。

- **時間を持つイベント**（音符、ドラム音、KeyOff、休符）： 待ち時間を読み取って INFO_WAIT_COUNT にセットし、そのフレームの処理を終える。次のフレームから待ち時間が減り始め、0 になったフレームで次のイベントをデコードする。
- **時間を持たないイベント**（音量、音色、ドラム音色、ジャンプ）： その場で状態を書き換え、**続けて次のイベントをデコードする**。つまり複数の設定イベントが同じフレームに重なってもすべて即座に適用される。

各イベントの処理内容は次のとおりである。

- **音符の KeyOn**： 音番号（0〜95）を周波数テーブルで周期値に変換して INFO_TONE_FREQ にセットし、選択中の音色（INFO_SEL_SFONT）を「発音中の音色」として取り込み、エンベロープを AR 状態から再開、ビブラートを初期化する。音色からはビブラート遅延時間とノイズ周波数も取り込む。
- **ドラム音の KeyOn**： ドラム用音色（後述の 3.7 節）の「ドラム用基準周波数」を INFO_TONE_FREQ にセットし、それ以外は音符の KeyOn と同じ初期化を行う。
- **KeyOff**： エンベロープを RR 状態へ移す（すでに RR 以降なら何もしない）。音が消えるのではなく、リリースの減衰が始まる。
- **休符**： エンベロープを停止状態にし、エンベロープ音量を 0 にする。即座に無音になる点が KeyOff と異なる。
- **音色設定**： 「選択中の音色」を更新する。発音中の音色そのものは次の KeyOn まで切り替わらない。ただし副作用として、発音中チャンネルのエンベロープ状態・ビブラート位置も初期化される（エンベロープは AR からやり直しになるが、パラメータは発音中の音色のものが使われる）。
- **ジャンプ**： 読み取り位置を、曲データ先頭からのオフセットで指定された位置へ移す。MML の $（ループ）で使われる。
- **演奏終了**： INFO_PLAY_ADR を 0 にし、そのチャンネルを停止状態にする。

## 3.4 音程と周波数テーブル

音番号 0〜95 は、ドライバ内のテーブル freq_data で PSG の周期値（トーンピリオド）に変換される。テーブルは C1（音番号 0）= 3420 から始まり、半音ごとに 96 個の値が並ぶ。PSG の発振周波数は「PSG クロック ÷（16 × 周期値）」であり、MSX の PSG クロック 1789772.5Hz では、例えば次のようになる。

| 音 | 音番号 | 周期値 | 周波数（計算値） |
|---|---:|---:|---:|
| C1 | 0 | 3420 | 約 32.7Hz |
| C4 | 36 | 427 | 約 261.9Hz |
| A4 | 45 | 254 | 約 440.4Hz |
| B8 | 95 | 14 | 約 7990Hz |

高音側では周期値の刻みが粗くなるため音程の精度は落ちる（API リファレンスも、最高音域で A#8 と B8 が同じ値 14 になることを注記している）。

なお、ミキサーは実効周波数の上位バイトの bit7 が立っている場合に「トーン停止」と判定する（3.8 節）。通常の音符では起こらないが、ドラム用基準周波数や効果音の周波数に 8000h を指定すると、この仕組みで意図的にトーンだけを止めてノイズだけを鳴らすことができる。

## 3.5 エンベロープ処理

音量の時間変化は、PSG のハードウェアエンベロープを使わず、ソフトウェアの状態機械で生成する。内部音量 INFO_ENV_VOL は 0〜255 の 8 ビット値で、フレームごとに音色のパラメータ（AR／DR／SL／SR／RR）に従って増減する。

| 状態 | 動作 | 遷移条件 |
|---|---|---|
| AR（アタック） | ENV_VOL に AR を加算する | 255 を超えたら 255 に固定し、DR へ |
| DR（ディケイ） | ENV_VOL から DR を減算する | SL を下回ったら SL に固定し、SR へ |
| SR（サスティン） | ENV_VOL から SR を減算する | 0 を下回ったら 0 に固定し、停止状態へ |
| RR（リリース） | ENV_VOL から RR を減算する | 0 を下回ったら 0 に固定し、停止状態へ |
| 停止 | 何もしない（ENV_VOL は 0 のまま） | ― |

ポイントは、SR がいわゆるサスティンレベルで保持するのではなく「SL まで下がった後も、遅い速度で減衰し続ける」段階だということである。SR を 0 にすれば SL で保持し続けるエンベロープになる。KeyOff イベントが来ると、AR／DR／SR のどこからでも RR へ移る。休符では即座に停止状態＋音量 0 になる。

PSG へ出す実効音量は、次の式で計算される。

```
実効音量 = max(0, (ENV_VOL >> 4) - (15 - 設定音量))
```

つまり内部音量の上位 4 ビット（0〜15）から、設定音量の「15 からの不足分」を差し引く。設定音量 15 なら内部音量がそのまま出て、設定音量が小さいほど全体が下がる。さらにミキサーでは、フェードアウト用のマスター音量（3.10 節）が引かれて最終的な PSG の音量レジスタ値になる。

## 3.6 ビブラート処理

音色データの先頭 32 バイトは**ビブラート波形**である。発音中、フレームごとに波形を 1 ステップずつ読み、符号付きの値として設定周波数（周期値）に加算したものが実効周波数になる。32 ステップで 1 周し、ループし続ける。波形の値が周期値への加減算であるため、値の正負と音程の上下は逆転する（周期値が増えると音は低くなる）ことに注意する。

ビブラートの開始は音色の「ビブラート遅延時間」だけ遅らせることができる。KeyOn の直後は遅延時間がカウントダウンされ、その間は実効周波数＝設定周波数のままになる。遅延が明けると波形の先頭（インデックス 0）から加算が始まる。

波形が 32 個の生データであるため、正弦波的な滑らかなビブラートから、矩形波状の急激な音程変化（いわゆるトリル的な効果）まで、値を並べることで自由に作れる。サンプルの音色では ±3 程度の小さな値が緩やかな波を描くように並んでおり、浅いビブラートとして使われている。

なお、この 32 バイトについて、付属の MML コンパイラの readme には「音量に対する増減値」と書かれているが、ドライバの実装では上記のとおり周波数（周期値）への加算に使われている。本書は実装に合わせて記述した（付録 B）。

## 3.7 ドラム音

ドラム音は、通常の音色を「ドラム用」として割り当て、トーンとノイズの組み合わせで打楽器を模す仕組みである。

- ドラムは 5 種類（ドラム 1〜5）あり、それぞれに音色を 1 つ割り当てる。割り当ては曲データのドラム音色設定イベント（107〜111）で行い、**ドライバ全体で共有されるグローバルな設定**である（チャンネルごとではない）。
- ドラム音の KeyOn（96〜100）では、音程の代わりに、そのドラムに割り当てられた音色の「ドラム用基準周波数」（音色データのオフセット 39〜40、16 ビット）が設定周波数になる。エンベロープとビブラート、ノイズは通常の音符と同じ処理を受ける。
- ドラム用基準周波数に 8000h を指定するとトーンが止まり、ノイズだけのドラムになる。mc.exe のテストデータ（mml_compiler/source/test1）では、ノイズ周波数に 128＋31＝159、ドラム用基準周波数に 32768 を指定した音色がドラム用として使われており、これが典型的なノイズ系ドラムの作り方である。

ドラム音色の割り当てが全チャンネル共有であるため、複数チャンネルからドラムを使う場合は、割り当ての変更が他チャンネルの演奏にも影響することに注意する。

## 3.8 ミキサーと PSG レジスタ

ミキサー（bgmdriver_mixer）は、計算済みの状態を PSG レジスタへ書き出す唯一の場所で、次の順序で処理する。

1. ch0、ch1 の実効周波数を REG#0〜3 へ書く。各チャンネルについて、ノイズが有効なら、そのノイズ周期を「ノイズ周期の候補」として覚える。
2. ch2 については、効果音が再生中かどうかで分岐する。再生中なら効果音の周波数と音量を REG#4、#5、#10 へ書く。再生中でなければ BGM ch2 の実効周波数を書く（3.9 節）。
3. ノイズ周期を REG#6 へ書く。
4. トーン／ノイズの有効・無効を REG#7（ミキサー）へ書く。
5. ch0、ch1（と BGM 時は ch2）の実効音量からマスター音量を引いたものを REG#8〜10 へ書く。効果音の音量はマスター音量の影響を受けない。

REG#7 の値は、各チャンネルの「トーン有効」「ノイズ有効」のフラグを集め、ポート方向のビット（bit7 = 1： ポート B 出力、bit6 = 0： ポート A 入力）を加えて反転したものである。「トーン有効」は実効周波数の上位バイト bit7 が 0 のこと、「ノイズ有効」は INFO_NOISE_FREQ の bit7 が立っていること（効果音側も同じ約束）で判定される。

ノイズ周期は PSG に 1 つしかないため、複数チャンネルがノイズを有効にしている場合は、**後に処理されたチャンネルの値が優先される**（処理順は ch0 → ch1 → ch2 のため、実質的に ch2 が最優先）。ミキサーは「ノイズ周期の候補」を変数 play_noise_freq に上書きしながら進み、最後に残った値を REG#6 へ書く。効果音がノイズを使う場合は、効果音の値が REG#6 へ直接書かれて BGM 側の調停は行われない。

REG#11〜13（ハードウェアエンベロープ関連）は、初期化時（bgmdriver_mute_psg）に 0 が書かれるだけで、演奏中は一切使われない。

## 3.9 効果音の処理と優先

効果音は、専用の小さなコマンド列（第 6 章）を解釈する独立したシーケンサで処理される。状態は、再生中フラグ、待ち時間、周波数、ノイズ周波数、音量、読み取り位置、そして**優先度**からなる。

再生開始（bgmdriver_play_sound_effect）では、まず優先度の判定が行われる。効果音データの先頭バイトが優先度であり、**数値が小さいほど優先度が高い**。再生中の効果音の優先度より、指定された効果音の優先度が**高い（数値が小さい）か等しい**場合にだけ、新しい効果音が再生を開始し、再生中の効果音は打ち切られる。優先度が低い（数値が大きい）指定は無視される。効果音が終わると優先度は最低（255）にリセットされるので、停止中であればどんな効果音でも再生できる。

効果音の再生中、ミキサーは ch2 の出力を効果音に切り替える。この間も BGM ch2 の演奏処理（デコード、エンベロープ、ビブラート）は通常どおり進み続けるが、その音は PSG へ出ない。効果音が終わると、BGM ch2 はその時点で進行している内容から聞こえるようになる。つまり効果音は BGM の第 3 チャンネルを「間借り」するのであって、BGM の演奏を止めるわけではない。

効果音コマンドの解釈は、待ち時間（BGM_SE_WAIT）に達するまで 1 フレーム内に連続して実行される。周波数・音量・ノイズ周波数の設定コマンドは即座に効果音用変数へ反映され、ミキサーがそのフレームの出力に使う。

## 3.10 フェードアウト

フェードアウトは、マスター音量（play_master_volume、0 = 最大、15 = 無音）を一定間隔で 1 ずつ増やしていく仕組みである。bgmdriver_fadeout に渡した速度 A が「音量が 1 段階下がる間隔（フレーム数）」になり、15 段階下がりきると演奏中の全チャンネルの演奏情報を初期化して演奏を停止し、マスター音量を 0 に戻す。

ミキサーは BGM 各チャンネルの実効音量からマスター音量を引き、0 未満にならないよう丸めて PSG へ書く。効果音の音量からは引かれないため、フェードアウト中でも効果音は元の音量で鳴る。

新しい曲の演奏開始（bgmdriver_play）や明示的な停止では、フェードアウト状態は解除される。

# 第4章 曲データの作り方

## 4.1 作成の流れ

曲データは、MML（Music Macro Language）で書いたテキストを専用コンパイラ mc.exe で変換して作るのが標準の方法である。全体の流れは次のとおりである。

1. MML テキスト（例： music.txt）を書く。
2. mc.exe でコンパイルし、アセンブリソース（music.asm）を得る。`mc.exe music.txt music.asm`
3. music.asm を ZMA でアセンブルし、バイナリ（music.bin）を得る。`zma music.asm music.bin`
4. music.bin を自分のプログラムに組み込み（または読み込み）、先頭アドレスを bgmdriver_play に渡す。

リポジトリには、この流れをまとめた compile.bat が 2 か所にある。

- mml_compiler/compile.bat： `mc sample.txt sample.asm` の後、`zma sample.asm sample.bin` を実行する最小例。
- sample/compile.bat： `..\mml_compiler\mc.exe xeviyoke.txt bgm.asm` で曲データを生成し、`..\tool\zma.exe sample.asm .\BGMSMPL.BIN` でサンプルプログラム全体をアセンブルする。

作った曲をすぐに試聴したい場合は、simple_player_for_z88dk の SPLAY.COM が便利である。music.bin と BGMDRV.BIN、SPLAY.COM を MSX-DOS のディスクに置き、`splay music.bin` で再生できる。再生中に L キーでファイルの再読み込み、P キーで再生開始ができるため、MML を直しては聴く、という確認作業に向いている（7.3 節）。

mc.exe は Windows 用の実行ファイルである。そのソースコード（mml_compiler/source/mc.c）も同梱されており、本章の記述は mc.c と付属 readme の両方に基づいて、食い違う点は mc.c の実装を優先した。

## 4.2 MML ファイルの構造

MML ファイルは、波括弧で囲まれた 4 つのブロックからなる。

```
{
	<音色定義データ>
}
{
	<ch0 の MML>
}
{
	<ch1 の MML>
}
{
	<ch2 の MML>
}
```

- 最初のブロックが音色定義で、定義した順に @0、@1、@2… と番号が振られる。
- 続く 3 ブロックが BGM の 3 チャンネル分である。**ブロックは必ず 3 つ必要**で、使わないチャンネルは空ブロック `{ }` とする（コンパイルは 3 チャンネル分を固定で行うため、ブロックが足りないとエラーになる）。
- `;` から行末まではコメントである。
- 英字コマンドは大文字・小文字を区別しない。空白と改行は自由に使える。

## 4.3 音色定義

音色 1 つは、**40 個の数値**で定義する。並びは次のとおりである。

| 順序 | 個数 | 内容 |
|---|---|---|
| 1〜32 | 32 | ビブラート波形（符号付き）。1 個が 1 フレーム（1/60 秒）に対応し、32 ステップでループする。設定周波数（周期値）への加算値 |
| 33 | 1 | AR（アタックレイト）。1〜255。大きいほど速く立ち上がる。255 で即座に最大 |
| 34 | 1 | DR（ディケイレイト）。最大音量から SL まで下がる速度 |
| 35 | 1 | SL（サスティンレベル）。DR から SR へ切り替わる音量（0〜255） |
| 36 | 1 | SR（サスティンレイト）。SL まで下がった後、さらに減衰する速度。0 なら SL で保持 |
| 37 | 1 | RR（リリースレイト）。KeyOff 後の減衰速度 |
| 38 | 1 | ビブラート遅延時間。KeyOn からビブラートが始まるまでのフレーム数 |
| 39 | 1 | ノイズ周波数。**128＋周期（0〜31）**でノイズ有効、128 未満（0 など）ではノイズ無効 |
| 40 | 1 | ドラム用基準周波数（16 ビット値）。ドラム音として使った場合の周期値。32768（8000h）でトーン停止（ノイズのみ） |

エンベロープの各値の意味とドライバ側の処理は 3.5 節を参照のこと。数値は 10 進で書き、負数は `-` を付ける（ビブラート波形用）。音色データは、コンパイル時に 1 音色＝41 バイトのバイナリへ変換され、曲データの後ろに並べられる（第 5 章）。

mml_compiler/sample.txt の音色 @0 を例にすると、波形は `0 1 2 2 2 0 -2 -3 …` という ±3 程度の緩やかな波、AR=255（即立ち上がり）、DR=2、SL=224、SR=1、RR=30、ビブラート遅延=20、ノイズ=0（無効）、ドラム用基準周波数=0、という指定である。

注意点を 2 つ挙げる。

- ノイズ周波数の指定方法について、付属 readme には「0 にするとノイズ無し」とだけあるが、ドライバ側の実装では bit7（128）がノイズ有効フラグである。ノイズを混ぜたい場合は **128＋周期** を書く必要がある（例： 周期 31 なら 159）。
- 定義する数値の個数が 40 個に満たない、あるいは多い場合、コンパイラは検査せず次の音色やブロックの数値を読み進めてしまう。個数の数え間違いは、そのまま音色のずれとして現れるので注意すること。

## 4.4 MML コマンドリファレンス

チャンネルブロックで使えるコマンドを、mc.c の実装に基づいて示す。初期状態は、テンポ 120、デフォルト音長 4、音量は未設定、ゲート比 8、オクターブは o5 の位置である。

### 音符（c d e f g a b）

ドレミファソラシに対応する。後ろに音長（分音符の数値）と付点を付けられる。`+` または `#` で半音上げ、`-` で半音下げる。

```
c4		四分音符のド
d4.		付点四分音符のレ
b16-	十六分音符のシ♭
a16+	十六分音符のラ♯
```

音長を省略すると l コマンドのデフォルト音長が適用される。音番号への変換は「（オクターブ−1）×12＋音名のオフセット（c=0、d=2、e=4、f=5、g=7、a=9、b=11）＋臨時記号」で、0〜95 の範囲外になるとエラーが表示される（データ出力は継続する）。

### ドラム音（h i j k m）

ドラム 1〜5 に対応する音符である。音長は音符と同じ書き方ができる。どの音色で鳴らすかは @h などのコマンドで割り当てる（4.4 節「@」参照）。ドラムの仕組みは 3.7 節を参照のこと。

### 休符（r）

休符。音符と同じように音長と付点を指定できる（例： r4.）。休符はエンベロープを即座に停止させる（3.3 節）。

### t（テンポ）

`t<数値>` でテンポを指定する。範囲は 20〜240 で、範囲外はエラー表示のうえ 120 として処理される。

重要なのは、**テンポはコンパイル時に音長をフレーム数へ換算するためだけに使われ、曲データには残らない**こと、そして**チャンネルごとに独立**していることである。各チャンネルのコンパイルはテンポ 120 から始まるため、曲全体のテンポを揃えるには、使う全チャンネルの先頭に同じ t を書く必要がある。付属 readme には「どのチャンネルに記述しても、全チャンネルに影響を及ぼします」とあるが、実装上の扱いは本節のとおりである（付録 B）。

### v（音量）

`v<数値>` で音量を 0〜15 で指定する。曲データの音量設定イベント（VOL）になり、そのチャンネルの設定音量を切り替える。PSG へ出る実際の音量は、エンベロープとの合成で決まる（3.5 節）。15 を超える値はエラー表示のうえ 15 に丸められる。なお、**v を一度も書かないチャンネルは設定音量 0 のまま、つまり無音**になるので、各チャンネルの先頭で必ず指定すること。

### q（ゲート比）

`q<数値>` で、音長のうち実際に音を鳴らす（KeyOff しない）割合を 1〜8 で指定する。q8 が音長の最後まで鳴らし続ける指定で、例えば q4 なら音長の半分で KeyOff し、残り半分はリリース（RR の減衰）に充てられる。コンパイラは、音長を「発音部」と「KeyOff 後の残り」に分割し、間に KeyOff イベントを挟んだデータを出力する（第 5 章）。範囲外の値はエラー表示される（処理は継続する）。

### l（デフォルト音長）

`l<数値>` で、音符・休符・ドラム音に音長を省略したときに適用される音長を指定する。初期値は 4。数値なしで書くと 4 に戻る。

### &（タイ）

直前の音と次の音をつなげる。コンパイラ内部では、& の付いた音の長さを蓄積し、次の同じ高さの音に合算して 1 つの音として出力する（再 KeyOn しない）。高さの違う音に & が付いた場合は、蓄積した長さで前の音を確定させてから新しい音を始める。readme の説明どおり `c4&c8` は `c4.` とほぼ等価である（フレーム換算の丸めの分だけ差が出ることがある）。

### o、>、<（オクターブ）

`o<数値>` でオクターブを 1〜8 で指定する。`>` で 1 つ上げ、`<` で 1 つ下げる。範囲外になる指定はエラー表示され、o では初期位置（o5 相当）に、> では最大（o8 相当）に、< では最小（o1 相当）に戻される。

### $（ループ）

そのチャンネルのループ開始位置を記録する。チャンネルの終わりまで演奏すると、PLAY_END の代わりにジャンプイベントが出力され、$ の位置へ戻って演奏が繰り返される。$ がないチャンネルは、終わりまで演奏すると停止する。1 チャンネルに複数書くと警告が表示され、**最後の $ が有効**になる。チャンネルごとに位置を指定できるため、チャンネル間でループの長さが違う曲も作れる（位相がずれていくので、意図した場合にだけ使うこと）。

### @（音色指定）

`@<番号>` で、そのチャンネルが次に KeyOn する音から使う音色を切り替える。番号は音色定義の順序（0 始まり）で、未定義の番号を指定するとエラー表示のうえ @0 として処理される。

`@h<番号>`、`@i<番号>`、`@j<番号>`、`@k<番号>`、`@m<番号>` は、ドラム 1〜5 への音色の割り当てである。例えば test1 の MML では ch2 の先頭で `@h2@i3` と書き、ドラム 1 に音色 @2、ドラム 2 に音色 @3 を割り当てている。ドラム音色の割り当てはドライバ全体で共有される（3.7 節）。

なお、**@ を一度も書かないチャンネルは、ドライバ側の「選択中の音色」が初期値 0 のまま**であり、正しい音色で鳴らない。各チャンネルの先頭で必ず @ を指定すること（v と同じく、実質的に必須の初期指定である）。

## 4.5 音長から待ち時間への変換

コンパイラは、音長を次の式でフレーム数（待ち時間）に換算する。

```
フレーム数 = 14400 ÷ (テンポ × 音長) × (ゲート比 ÷ 8)
```

14400 は「1 分＝3600 フレーム」× 4（四分音符基準）から来る定数である。例えばテンポ 144 の四分音符は 14400÷(144×4)＝25 フレームになる。

換算には 2 つの工夫がある。

- **誤差の蓄積**： 割り切れない場合の端数は切り捨てずに「累積誤差」として保持し、次の音符の換算に加える。これにより、例えば 12 分音符が 8.33 フレームになるような場合でも、8、8、9、8… と配分されて曲全体の長さがずれない。mml_compiler/sample.txt（テンポ 144、l12）のコンパイル結果が、音長の並び 7、7、8、7…（後述の −1 を含む）になるのはこの配分の現れである。
- **−1 の調整**： ドライバ側では、イベントは「待ち時間＋1 フレーム」持続する規約であるため（3.3 節）、コンパイラは出力時にフレーム数から 1 を引く。さらに、待ち時間が 255 を超える場合は 255 ずつの分割で出力される（5.3 節）。

タイ（&）でつながれた音は、フレーム数を合算してから 1 つの音として出力される。

## 4.6 コンパイル時のメッセージ

mc.exe は、標準出力に音色の個数と各チャンネルのデータサイズを表示し、正常終了すると `Completed.` と表示する。エラーは標準エラー出力に、行番号付きの日本語メッセージで表示される。主なものは次のとおりである。

| メッセージ | 意味 |
|---|---|
| 音色設定が見つかりません | 先頭ブロックの `{` がない |
| 曲データが見つかりません | チャンネルブロックの `{` がない（ブロック不足など） |
| 音色データが１つもありません | 音色定義が 0 個 |
| 音程指定が範囲外です | 音番号が 0〜95 を外れた |
| T の指定が範囲外です | テンポが 20〜240 の範囲外（120 で処理継続） |
| Q の指定が範囲外です | ゲート比が 1〜8 の範囲外 |
| @ の指定が範囲外です | 未定義の音色番号（@0 で処理継続） |
| V の指定が範囲外です | 音量が 15 超過（15 で処理継続） |
| O の指定が範囲外です／> 指定により…／< 指定により… | オクターブが 1〜8 の範囲外 |
| 解釈できない記号があります | 文法にない文字 |
| WARNNING: 同一チャンネル内に $指定が複数存在します | $ の重複（最後が有効） |

エラーが表示されても、多くの場合は代替値で処理が継続し、出力ファイル自体は生成される。メッセージが出たら、まず該当行を直してから使い直すこと。なお内部バッファは音色データ・曲データとも 32KB で、これを超える規模の曲は扱えない。

## 4.7 生成されたデータの組み込み

mc.exe の出力（.asm）は、`db` 命令でバイト列を並べたアセンブリソースである。前半が「曲データ」、後半が「音色データ」の 2 セクションに分かれている。これを include した位置が、そのまま bgmdriver_play に渡す曲データの先頭になる。

```
bgm001::
		include		"bgm.asm"		; mc.exe が生成したファイル
```

sample/ では、sample.asm の中でドライバ本体の直後にこの形で取り込んでいる。生成された .asm をアセンブルせず、バイナリ（.bin）として別ファイルにしておき、実行時に読み込んで使う形でもよい。その場合は、読み込み先のアドレスを bgmdriver_play に渡す。どちらの場合も、データの置き場所は割り込み処理中に参照できる領域（ページ 0 を避ける）にすること（2.1 節）。

# 第5章 曲データの形式

本章では、mc.exe が生成する曲データのバイナリ形式を、ドライバ側のデコード処理と突き合わせて規定する。独自の MML コンパイラを作りたい場合や、データを手作業で調整したい場合の資料である。通常の利用では本章を読む必要はない。

## 5.1 全体構造

曲データは、先頭のヘッダ、各チャンネルのデータ列、音色データ群がこの順に並んだ、自己完結したバイト列である。すべてのオフセットは**曲データの先頭アドレスからの相対値**であるため、データ全体をどのアドレスに配置しても、そのまま使える。

```
+0    ch0 データへのオフセット（2 バイト、リトルエンディアン）
+2    ch1 データへのオフセット（2 バイト）
+4    ch2 データへのオフセット（2 バイト）
+6    ch0 のデータ列
      ch1 のデータ列
      ch2 のデータ列
      音色データ群（41 バイト × 音色数）
```

bgmdriver_play は、ヘッダの 3 つのオフセットに曲データの先頭アドレスを加えて、各チャンネルの読み取り位置を初期化する。

## 5.2 イベント一覧

各チャンネルのデータ列は、イベントコードと付随データの列である。コードの値は bgmdriver_d.asm に定数として定義されている。

| コード | 定数名 | 付随データ | 意味 |
|---:|---|---|---|
| 0〜95 | （音番号） | 待ち時間 | 音符の KeyOn。音番号は 3.4 節の周波数テーブルを引く |
| 96 | BGM_DRUM_1 | 待ち時間 | ドラム 1 の KeyOn |
| 97 | BGM_DRUM_2 | 待ち時間 | ドラム 2 の KeyOn |
| 98 | BGM_DRUM_3 | 待ち時間 | ドラム 3 の KeyOn |
| 99 | BGM_DRUM_4 | 待ち時間 | ドラム 4 の KeyOn |
| 100 | BGM_DRUM_5 | 待ち時間 | ドラム 5 の KeyOn |
| 101 | BGM_KEYOFF | 待ち時間 | KeyOff（エンベロープを RR へ移す） |
| 102 | BGM_REST | 待ち時間 | 休符（エンベロープを即時停止する） |
| 103 | BGM_VOL | 音量 1 バイト | 設定音量を 0〜15 に変更する |
| 104 | BGM_SOUND_FONT | オフセット 2 バイト | 選択中の音色を変更する |
| 105 | BGM_JUMP | オフセット 2 バイト | 読み取り位置を指定オフセットへ移す |
| 106 | BGM_PLAY_END | なし | そのチャンネルの演奏を終了する |
| 107 | BGM_DRUM1_FONT | オフセット 2 バイト | ドラム 1 の音色を割り当てる |
| 108 | BGM_DRUM2_FONT | オフセット 2 バイト | ドラム 2 の音色を割り当てる |
| 109 | BGM_DRUM3_FONT | オフセット 2 バイト | ドラム 3 の音色を割り当てる |
| 110 | BGM_DRUM4_FONT | オフセット 2 バイト | ドラム 4 の音色を割り当てる |
| 111 | BGM_DRUM5_FONT | オフセット 2 バイト | ドラム 5 の音色を割り当てる |

待ち時間を持つイベント（0〜102）は、コードの直後に 5.3 節の待ち時間が続く。音量・音色・ジャンプのイベントは時間を持たず、ドライバは同じフレームのうちに続けて次のイベントを処理する。

MML との対応で注意すべき生成規則は、次の 2 点である。

- **ゲート比（q）が 8 未満の場合**、1 つの音符は「音符イベント（発音部の待ち時間）＋KeyOff イベント（残りの待ち時間）」の 2 イベントに分割して出力される。q8 の場合は音符イベントだけである。ドラム音も同様に分割される。休符は常に単一のイベントである。
- **ループ（$）がある場合**、チャンネルの末尾には PLAY_END の代わりに、$ の位置を指す JUMP イベントが置かれる。ジャンプ先オフセットは、ヘッダを含む曲データ全体の中での絶対オフセットである。

## 5.3 待ち時間の符号化

待ち時間は可変長で符号化される。読み取り規則は次のとおりである。

- バイトを読み、値が 255 なら合計に 255 を加えて次のバイトを読む。
- 255 でないバイトを読んだら、その値を合計に加えて終了する。

つまり待ち時間 W は、`255, 255, …, r`（最後の 1 バイト r は残り）という並びで表され、W = 255×（255 の個数）＋ r である。1 バイトで表せるのは 0〜254、255 は `255, 0` の 2 バイトになる。

ドライバ内部では、イベントは「デコードしたフレーム＋待ち時間のフレーム数」だけ持続する。すなわち符号化された値 W のイベントは、合計 W＋1 フレームを占める。mc.exe はこの規約に合わせて、換算したフレーム数から 1 を引いた値を符号化している（4.5 節）。

## 5.4 音色データの形式

音色データは 1 つ 41 バイトで、曲データの末尾に定義順に並ぶ。レイアウトはドライバ内の SFONT_* 定義そのものである。

| オフセット | サイズ | 内容 |
|---:|---:|---|
| 0〜31 | 32 | ビブラート波形（符号付きバイト×32） |
| 32 | 1 | AR |
| 33 | 1 | DR |
| 34 | 1 | SL |
| 35 | 1 | SR |
| 36 | 1 | RR |
| 37 | 1 | ビブラート遅延時間（フレーム数） |
| 38 | 1 | ノイズ周波数（bit7 = 有効フラグ、下位 5 ビット = 周期） |
| 39〜40 | 2 | ドラム用基準周波数（16 ビット、リトルエンディアン） |

MML の音色定義では 40 個の数値を書くが、最後の「ドラム用基準周波数」が 16 ビット値として 2 バイトに格納されるため、バイナリでは 41 バイトになる（4.3 節）。

曲データ中の音色設定イベントが持つオフセットは、この音色データ群の中の該当エントリを指す。mc.exe はコンパイル中、音色設定イベントの仮データとして「音色番号」を置いておき、全チャンネルのコンパイルが終わった後のリンク処理で、データ列を走査しながら「音色番号×41＋音色データ群の開始オフセット」へ書き換えている。

## 5.5 生成例の読み解き

mml_compiler/sample.txt をコンパイルした結果（sample.asm、80 バイト）を例に、形式を確認する。

```
06 00 16 00 26 00                                  ← ヘッダ: ch0=+6, ch1=+16h, ch2=+26h
67 0F                                              ← ch0: VOL 15
68 27 00                                           ← ch0: SOUND_FONT → オフセット 27h
30 07 32 07 34 08 35 07 37 10                      ← 音符 C5 D5 E5 F5 G5(タイ)
6A                                                 ← ch0: PLAY_END
67 0F 68 27 00 34 07 35 07 37 08 39 07 3B 07 6A    ← ch1
6A                                                 ← ch2: PLAY_END のみ（空チャンネル）
（ここまで 27h = 39 バイト）
00 01 02 02 …（32 バイト）                          ← 音色 @0 のビブラート波形
FF 02 E0 01 1E 14 00 00 00                         ← AR DR SL SR RR 遅延 ノイズ ドラム周波数
```

読み解きのポイントは次のとおりである。

- 音色データはオフセット 27h（39）から始まり、両チャンネルの SOUND_FONT がそこを指している。
- 音符は「音番号＋待ち時間」の 2 バイト組で並ぶ。待ち時間 07、07、08、07 は、テンポ 144・12 分音符の換算（8.33 フレーム）の誤差配分と −1 調整の結果である（4.5 節）。最後の G はタイで 2 つつながっているため、待ち時間が 10h（16）になっている。
- 空のチャンネルは PLAY_END 1 バイトだけのデータ列になる。
- 音色は 41 バイトで、末尾 9 バイトが AR 以降のパラメータである。

# 第6章 効果音データの作り方

## 6.1 効果音データの構造

効果音データは、MML のようなコンパイラを持たない。bgmdriver_d.asm に定義されたコマンド定数を並べたバイト列を、アセンブリソースや C の配列として手作業で作成する。

構造は単純で、先頭の 1 バイトが**優先度**、その後に**コマンド列**が続き、最後に BGM_SE_END を置く。

```
db		32					; 優先度
db		BGM_SE_VOL			; コマンド
db		12					; （パラメータ）
db		BGM_SE_FREQ
dw		30
		…
db		BGM_SE_END			; 終端
```

効果音は PSG の ch2（チャンネル C）を使って再生され、和音は出せない。トーンとノイズは同時に出すことができる。再生の仕組みと BGM との競合については 3.9 節を参照のこと。

## 6.2 コマンドリファレンス

コマンドは 5 種類で、値は bgmdriver_d.asm（および z88dk 用の bgmdriver.h）に定義されている。ドライバは、待ち時間（BGM_SE_WAIT）か終端（BGM_SE_END）に達するまで、1 フレームのうちにコマンドを連続して実行する。5 以上の値はドライバ側で終端と同じ扱いになる。

| コマンド | 値 | パラメータ | 意味 |
|---|---:|---|---|
| BGM_SE_FREQ | 0 | 周期値 2 バイト（リトルエンディアン） | トーンの周期値を設定する。小さいほど高い音。**8000h を指定するとトーン停止**（ノイズのみの効果音にする場合に使う） |
| BGM_SE_VOL | 1 | 音量 1 バイト（0〜15） | 効果音の音量を設定する。フェードアウトの影響は受けない |
| BGM_SE_NOISE_FREQ | 2 | 1 バイト | ノイズの設定。**bit7 = ノイズ有効フラグ**で、有効にする場合は 128＋周期（周期は 0〜31）を指定する。bit7 が 0 の値では効果音のノイズは鳴らない |
| BGM_SE_WAIT | 3 | フレーム数 1 バイト（1〜255） | 現在の設定を保ったまま、指定フレーム数だけ待つ |
| BGM_SE_END | 4 | なし | 効果音を終了する |

各コマンドの詳細を述べる。

### BGM_SE_FREQ

周期値は PSG の REG#4（下位）／REG#5（上位）に相当する値で、BGM の音程と同じテーブル（freq_data、3.4 節）が目安になる。例えば C4 の音程なら 427、A4 なら 254 である。テーブルの値にこだわる必要はなく、中間の値や、時間とともに周期値を滑らかに変える指定（スイープ）も自由に行える。範囲は実質 0〜4095 で、特別な値として 8000h が「トーン停止」を意味する（ミキサーが上位バイトの bit7 で判定するため）。

### BGM_SE_VOL

音量は PSG の REG#10 に相当する 0〜15 の値である。効果音にはエンベロープの仕組みはないので、音量の時間変化は BGM_SE_WAIT と組み合わせて段階的に書く。

### BGM_SE_NOISE_FREQ

ノイズ周期は PSG の REG#6 に相当し、値が小さいほど高い周波数のノイズになる。ここで注意が必要なのは有効フラグの扱いで、ドライバのミキサーは**値の bit7 が立っている場合にだけ**、その値（下位ビット）をノイズ周期として採用し、効果音チャンネルのノイズを有効にする。したがってノイズを鳴らす場合は `20 + 0x80` のように 128 を加えた値を書く（リポジトリのサンプルはすべてこの形式である）。bit7 のない値（0〜31）を書いても、効果音のノイズは有効にならない。

既刊の API リファレンス 4.1.3 節には「0x80 を指定するとノイズを停止する」とあるが、ドライバの実装とは逆である。本書は実装に合わせて記述した（付録 B）。なお「ノイズを止める」には、bit7 を落とした値を書き直すか、効果音自体を BGM_SE_END で終えればよい。

また、ノイズ周期レジスタは PSG 全体で共通である。BGM 側のチャンネルがノイズを使っているときに効果音がノイズを使うと、その間、BGM 側のノイズの周期も効果音の値に変わる（3.8 節）。

### BGM_SE_WAIT

指定したフレーム数だけ、現在の周波数・音量・ノイズ設定を維持する。1〜255 が指定でき、60 で約 1 秒である。コマンド列はこのコマンドで区切ることで時間軸を持つ。長い待ちが必要な場合は、WAIT を複数並べる。

### BGM_SE_END

効果音の終了を示す。パラメータはない。これを置かないと、ドライバはメモリを読み進めてしまうため、必ず最後に置くこと。終了すると再生中フラグが下り、優先度が最低（255）にリセットされ、ch2 は BGM へ戻る。

## 6.3 優先度と競合

先頭の優先度は、**数値が小さいほど優先度が高い**。再生開始時の判定は次のとおりである（3.9 節）。

- 再生中の効果音より、新しい効果音の優先度が高い（数値が小さい）→ 再生中の効果音を打ち切って、新しい効果音を開始する。
- 優先度が等しい → 同様に、新しい効果音が開始される（後から指定した方が優先）。
- 新しい効果音の優先度が低い（数値が大きい）→ 指定は無視され、再生中の効果音が続く。
- 効果音が再生中でない → 優先度によらず開始される。

使い方の目安として、sample/ のサンプルでは、トーン系の効果音（sound_effect001）に 32、ノイズ系の効果音（sound_effect002）に 128 が与えられている。重要な効果音ほど小さい値を割り当て、連打され得る効果音同士は同値にしておくと「最後の入力が勝つ」自然な挙動になる。

BGM との競合については、効果音は BGM を止めない。再生中は ch2 の出力だけが効果音に置き換わり、BGM の ch2 は無音のまま進行する。ch0、ch1 は影響を受けない。フェードアウトも効果音の音量には影響しない。

## 6.4 作成方法

効果音データは、次のいずれかの形で作成する。

**アセンブリソースに直接書く**（sample/ の方式）。bgmdriver_d.asm の定数が使えるため、コマンド名でそのまま書ける。

```
sound_effect001:
		db		32					; priority [小さい方が優先]
		db		BGM_SE_VOL
		db		12
		db		BGM_SE_FREQ
		dw		30
		db		BGM_SE_WAIT
		db		1
		db		BGM_SE_FREQ
		dw		25
		…
		db		BGM_SE_END
```

**C の配列として書く**（z88dk の方式）。bgmdriver.h に同じ値のマクロ（BGM_SE_FREQ など）が定義されている。

```c
static const char se_data[] = {
	128,									/* 優先度 */
	BGM_SE_VOL, 12,
	BGM_SE_FREQ, 0x00, 0x80,				/* トーン停止（8000h） */
	BGM_SE_NOISE_FREQ, 20 + 0x80,			/* ノイズ有効、周期 20 */
	BGM_SE_WAIT, 5,
	…
	BGM_SE_END
};
```

再生は、どちらの場合もデータの先頭アドレスを API に渡すだけである（アセンブラなら HL に入れて bgmdriver_play_sound_effect、C なら bgmdrv_play_se( p_se_data )）。データの置き場所は、曲データと同様にページ 0 を避けること。

## 6.5 効果音の作例

リポジトリの作例から、設計のパターンを 2 つ紹介する。

**作例 1： 周期値スイープによるトーン系効果音**（sample/ の sound_effect001、優先度 32）

音量 12 を設定した後、周期値 30 → 25 → 20 → 10 → 30 → 25 → 20 → 10 と、各 1 フレームずつ切り替える。周期値が小さい＝高い音なので、短い間に音程が上下する電子音的な効果音になる。WAIT がすべて 1 フレームであり、全体で 8 フレーム（約 0.13 秒）の短い音である。

**作例 2： ノイズの周期変化による効果音**（sample/ の sound_effect002、優先度 128。z88dk サンプルの se_data もほぼ同じ内容）

最初に BGM_SE_FREQ で 32768（8000h）を指定してトーンを止め、ノイズだけを使う。ノイズ周期を 20 → 8 → 28 → 12 → 31 → 15 と、各 5〜10 フレームずつ切り替える。ノイズの質感が段階的に変わる、爆発音や打撃音を思わせる効果音である。

どちらの作例も、「設定コマンドを並べ、WAIT で時間を区切り、最後に BGM_SE_END」という最小の型でできている。音量を時間変化させたい場合は、WAIT の合間に BGM_SE_VOL を挟めばよい。

# 第7章 サンプルプログラムと応用

## 7.1 sample： BSAVE＋BASIC から使う

sample/ は、ドライバと曲データをひとまとめにした BSAVE 形式のバイナリ（BGMSMPL.BIN、A000h 配置）と、それを MSX-BASIC から呼び出すサンプル（BGMSMPL.BAS）である。ビルドは sample/compile.bat が担い、まず mc.exe で xeviyoke.txt（ゲーム風の短い曲）を bgm.asm へコンパイルし、次に zma で sample.asm をアセンブルする。

sample.asm の構成は、本書のここまでの内容の実地例になっている。

- 先頭で msx.asm（BIOS 関連の定義）を include し、BSAVE ヘッダを出力する。
- エントリポイント（A000h）で interrupt_initializer を呼び、H.TIMI フックを登録する。フック登録の実装は 2.2 節で解説したとおりである。
- 続けて play_bgm001 などの呼び出し口が並ぶ。BLOAD の ,R 実行でエントリポイントが呼ばれると、フック登録に続けて bgm001 の演奏まで開始される。
- ドライバ本体を include し、その直後に曲データ（bgm.asm）と、2 つの効果音データ（sound_effect001／002、6.5 節の作例）を配置する。

BGMSMPL.BAS は、USR 関数で各呼び出し口を叩く。

```
100 CLEAR 100,&H9FFF:DEFINTA-Z
110 BLOAD"BGMSMPL.BIN",R
130 DEFUSR0=&HA003		: REM play_bgm001
150 DEFUSR1=&HA00A		: REM stop_bgm001
170 DEFUSR2=&HA00E		: REM fadeout_bgm001
190 DEFUSR3=&HA012		: REM play_se001
210 DEFUSR4=&HA019		: REM play_se002
```

USR のアドレス（A003h、A00Ah、A00Eh、A012h、A019h）は、各呼び出し口の命令長（call = 3 バイト、ld hl = 3 バイト、ret = 1 バイト）と一致していることを、付録 A の検証で確認した。

## 7.2 sample_for_z88dk： C 言語から使う

sample_for_z88dk/ は、z88dk の C 言語からドライバを使うためのサンプル（BGMTEST.COM）である。ドライバを独立したバイナリ BGMDRV.BIN として分離し、C 側からは関数ポインタ経由で呼ぶ構成になっている。ビルド（build.bat）は 3 段階である。

1. `zma bgm_driver_for_z88dk.asm BGMDRV.BIN`： ドライバ本体に C 呼び出し用のラッパを付けた BGMDRV.BIN を作る。
2. `python makeup_bgmdriver_parameter.py`： zma のシンボル出力（zma.sym）から、各エントリポイントの絶対アドレスを集めた bgmdriver_param.h を生成する。
3. `zcc +msx -create-app -subtype=msxdos main.c bgmdriver.c -bn BGMTEST.COM`： 本体をコンパイルする。

BGMDRV.BIN の配置アドレスは config.txt の start_address で決める（サンプルでは A000h）。**4000h 以上でなければならない**理由は 2.1 節のとおりである。ラッパ（bgm_driver_for_z88dk.asm）は、H.TIMI フックの登録・復元（bgmdrv_setup_htimi／bgmdrv_restore_htimi）も含んでおり、フックは RST 30h（スロット間コール）経由でドライバを呼ぶ形になっているため、ドライバがどのページにあっても呼び出せる。

C 側の API は bgmdriver.h に宣言されており、アセンブラ版 API との対応は次のとおりである。

| C 関数 | 対応する処理 |
|---|---|
| bgmdrv_init() | BGMDRV.BIN を読み込み、フックを登録する。成功で 1、失敗で 0 |
| bgmdrv_term() | フックを復元する。終了前に必須 |
| bgmdrv_play( p_data ) | bgmdriver_play（関数ポインタ） |
| bgmdrv_stop() | bgmdriver_stop（関数ポインタ） |
| bgmdrv_check_play() | bgmdriver_check_playing。0 = 停止中、1 = 演奏中 |
| bgmdrv_fade_out( speed ) | bgmdriver_fadeout。speed は 1〜255（大きいほど遅い）。256 以上は 255 に丸められる |
| bgmdrv_play_se( p_data ) | bgmdriver_play_sound_effect（関数ポインタ） |
| bgmdrv_load_file( p, name, size ) | ファイルを 128 バイトずつ読み込むユーティリティ。size に 0 を指定するとファイル全体 |

main.c のサンプルは、曲データと効果音データを 6000h へコピーしてから（これもページ 0 回避のため）演奏を開始し、演奏終了を待って、効果音を 4 回鳴らして終了する、という流れである。曲データは mml_compiler のサンプル曲、効果音は 6.5 節の作例 2 とほぼ同じノイズ系のものである。

## 7.3 simple_player： 試聴ツール SPLAY.COM

simple_player_for_z88dk/ は、BGMDRV.BIN と曲データのバイナリを読み込んで再生するだけの簡易プレイヤー SPLAY.COM である（2023 年追加）。構成は 7.2 節のサンプルと同じ仕組みで、配置アドレスは C000h である。

使い方は readme にまとめられている。

1. MML をコンパイルして曲バイナリを作る（`mc.exe music.txt music.asm` → `zma music.asm music.bin`）。
2. MSX-DOS のディスクに SPLAY.COM、BGMDRV.BIN、music.bin を置く。
3. `splay music.bin` で再生する。再生中に L キーで再読み込み、P キーで再生開始ができる。

MML の試行錯誤にはこのツールが最も手軽である。openMSX を使う場合は、ディレクトリマウントしたフォルダに MSXDOS.SYS、COMMAND.COM と一緒に置くよう readme に案内がある。

## 7.4 カスタマイズの手がかり

ドライバは MIT ライセンスで、自分の都合に合わせた改変が認められている。改変の入口になりやすい箇所を挙げる。

- **音程を変えたい**： 周波数テーブル freq_data（bgmdriver.asm 末尾）を書き換える。周期値の並びがそのまま音程になる。
- **チャンネル数を減らしたい**： 割り込みハンドラが呼ぶ bgmdriver_play_ch の回数と、ミキサーの該当チャンネルの処理が対象になる。ただし曲データの形式（3 チャンネル前提のヘッダ）にも影響する。
- **効果音を複数チャンネルで鳴らしたい**： 現行の効果音シーケンサは ch2 専用である。ミキサーの ch2 分岐と効果音の状態変数が拡張点になる。
- **別のコンパイラを作りたい**： 第 5 章の形式仕様がそのまま使える。mc.c は 700 行弱の単一ファイルで、読み解く際の参考にもなる。

いずれの場合も、改変後は実機またはエミュレータでの動作確認を十分に行うこと（ライセンス上も、動作テストは利用者の責任とされている）。

## A.2 BGMDRV.BIN の 1 バイト相違について

simple_player_for_z88dk のソースから組み立てたバイナリは、同梱の BGMDRV.BIN と 1 バイトだけ異なった。相違箇所は、z88dk ラッパの bgmdrv_fade_out 内にある相対ジャンプ（jr nz, skip1）の変位バイトである。

- 現行ソースから組み立てた値： 変位 1。speed が 256 以上の場合、A に 255 を入れて bgmdriver_fadeout を呼ぶ（255 へのクランプとして動作する）。
- 同梱 BGMDRV.BIN の値： 変位 4。この場合、speed が 256 以上ではジャンプ先が呼び出しの後ろの ret になり、**フェードアウトが開始されない**。

同梱バイナリが現行ソースとは異なる版のソースから作られた可能性が高い。実害が出るのは C の bgmdrv_fade_out に 256 以上の値を渡した場合だけで、通常の範囲（1〜255）では両者は同じ動作をする。本書では現行ソースの動作に合わせて記述した。

# 付録B 既存資料との相違点

本書を作成するにあたり、リポジトリ付属の既存資料（MML コンパイラの readme、API リファレンス）とソースコードの実装を突き合わせたところ、記述と実装が食い違う箇所が見つかった。本書ではいずれも**ソースコードの実装に合わせて**記述した。ここに一覧を残す。

## B.1 音色データ先頭 32 バイトの意味

- 既存資料（mml_compiler/readme.txt）： 「32 個の符号付きのデータ。音量に対する増減値。1 個は 1/60 秒に対応」と説明されている。
- 実装（bgmdriver.asm）： この 32 バイトは SFONT_VIB_WAVE、すなわち**ビブラート波形**であり、発音中に設定周波数（周期値）へ符号付きで加算される。音量の計算には使われない。
- 本書の扱い： 3.6 節・4.3 節・5.4 節でビブラート波形として記述した。なお readme 自身に「10 年くらい前に作ったプログラムなので、思い出しながら記述。誤記があるかもしれません」と断り書きがある。

## B.2 テンポの効き方

- 既存資料（mml_compiler/readme.txt）： t コマンドについて「どのチャンネルに記述しても、全チャンネルに影響を及ぼします」と説明されている。
- 実装（mc.c）： テンポはチャンネルごとのコンパイル状態であり、各チャンネルの音長をフレーム数へ換算するときにだけ使われる。他チャンネルへは伝わらない。各チャンネルの初期テンポは 120 である。
- 本書の扱い： 4.4 節で「全チャンネルに同じ t を書く必要がある」と記述した。

## B.3 BGM_SE_NOISE_FREQ の有効フラグ

- 既存資料（API リファレンス 4.1.3 節）： パラメータは「0〜31」で、「0x80 を指定するとノイズを停止する」と説明されている。
- 実装（bgmdriver.asm のミキサー）： 値の **bit7 が立っている場合にノイズが有効**になり、その値の下位ビットがノイズ周期として使われる。bit7 のない値（0〜31）を指定しても、効果音のノイズは有効にならない。リポジトリのサンプル（sample.asm、z88dk の main.c）はすべて `周期 + 0x80` の形式で指定している。
- 本書の扱い： 6.2 節で実装どおりに記述した。BGM 側の音色データのノイズ周波数（5.4 節）も同じ約束（bit7 = 有効フラグ）である。

## B.4 同梱 BGMDRV.BIN と現行ソースの相違

simple_player_for_z88dk（および sample_for_z88dk）同梱の BGMDRV.BIN は、現行ソースから組み立てた結果と 1 バイト異なる。詳細は付録 A.2 節を参照のこと。通常の使用範囲では動作に差はない。
